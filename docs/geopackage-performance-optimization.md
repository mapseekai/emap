# GeoPackage 导入与 GPU 视图准备优化

> 本文保留前两批的测量。后续 4× 和回全图的处理与测量边界见
> [几何准备优化](geopackage-zoom-performance.md)。

## 导入与几何复用能力

基线 `a68a9bd8`。使用完整 `brandenburg.gpkg`（1,048,797,184 字节、20 个表、
5,028,831 条源记录），保留共享拓扑、默认 DisplayArcs、点 LOD、图层样式与几何预算。
优化面向完整数据的分批传输、主线程恢复和视图覆盖复用；源文件、共享拓扑和预算均保留。

## 第一批：导入与主线程恢复

CPU profile 发现两类非必要成本：扫描/解码每 4,096 行的嵌套零时长定时器等待，
以及整个结果通过单条 postMessage 序列化/反序列化。另有逐属性 defineProperty 热点。

- 扫描检查点按 8 ms 时间片通过本次导入拥有的 MessageChannel 让步，成功/失败均关闭。
- 普通属性直接赋值；`__proto__` 仍显式定义为自有数据属性，64 位整数与 Boolean 规则不变。
- 完成拓扑后按最多 4,096 行分批发送；发送端等待确认才发下一批，不让消息队列无限增长。
- 路径按 feature/part 数量及有符号 arc ID 转移；点保持 Float64 坐标。接收侧恢复可编辑数组。
- BLOB 属性按批复制，而非提前转移可能在不同几何维度记录间共享的 buffer。
- 接收侧不对外暴露暂存 Dataset；顺序、行数和完整性校验通过后才发布，取消则丢弃暂存。
- 单个超大要素保持完整；4,096 限制每批行数，属性 BLOB 大小另受其字节预算约束。

M4 / Chrome 153，1280×852 DPR 1，三个后端初步各一次：导入 22.7–25.7 秒，
完整提交 24.7–31.0 秒，首次最长主线程任务 2.28–2.37 秒；均完成 503 万记录核对与释放。
以上为每后端一次的初步样本；最终多轮对照另行记录。主线程原生 ArcCollection 与 DisplayArcs 初始化
仍有不可中断工作，数据传输与恢复仍有复制成本。

验收：GeoPackage 单元/集成 32 项通过；浏览器导入、主线程等价和取消 3 项通过；
typecheck、类型契约、测试布局、架构、生产代码 lint、库/示例构建通过。
原始采样与测量目录 `/tmp/emap-gpkg-opt-ix7eec9h`，源文件哈希未变化。

## 第二批：覆盖复用与渐进帧成本

复用已经驻留、覆盖范围完整包含新请求的面几何。只复用相同成员、源版本、弧段身份、
LOD interval 和无 screen-space 变换的 fill；扩大到原覆盖之外或改变 detail 仍须重建。
更小视图使用原有 FillRangeIndex 裁剪，源数据、图层顺序、透明混合和精度不变。

渐进帧成本从 clear() 开始累计，而不再只统计 finishFrame() 内的 GPU 提交；
既有自适应通知因此也考虑图层选择与命令组装。首反馈和完成帧通知的既有规则不变。

曾实验单 Worker 下的有界提前打包，但没有得到可靠的整体收益且复杂度明显增加。
与关闭提前打包的独立对照后撤掉该实验，未提交。最终仍使用原来的串行有界 Worker
调度，没有新增 Worker、CPU/GPU 缓存或提高预算。被撤掉的实验结果独立保留，
不作为最终版本的验收数据。

覆盖复用减少新视图构建，但可能保留较大 mesh 的更多可见区间，增加稳定帧 draw calls；
冷视图完成和稳定帧分别计时。全图与 4× 的合计工作集仍无法全部常驻于
原来的软预算，回全图仍可能重新准备。

## 升级与复测

本次改变内部 GeoPackage Worker 消息协议；主库和 `emap-geopackage-worker.js` 必须来自
同一次构建。使用自定义 workerUrl 的宿主也需要更新对应资源并刷新旧缓存。
公共导入调用方式没有改变。

```sh
pnpm examples:luma
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgl2 --cycles 1 --warm-frames 12 --gpu-frames 8
```

将 renderer 换为 webgpu 或 canvas2d 可复测另外两种后端。此命令使用生产查看器和完整文件。

## 最终实测（撤掉提前打包后重新运行）

基线与最终版本均为 M4 / 16 GiB / Chrome 153.0.8010.53，1280×852 CSS、DPR 1。
每后端三个独立浏览器，共九次，顺序轮换。以下为中位数，单位秒。
不包括网页/GPU 初始化；计时从选好文件后的读取开始，OS 文件缓存未清空。
首次完整时间记录场景提交；合成器首像素需单独测量。固定视图更新包括静默确认开销。

两 GPU 后端到 16× 累计覆盖复用 96 次，到 32× 累计 189 次，对应少构建 96 和新增 93 个条目。
4× 没有覆盖复用，回全图仍重建原来的低细节条目；两项均不视为已解决。
WebGPU 4× 三次为 5.384–7.213 秒，中位数比基线更慢；收益主要出现在本轮已列出的近景覆盖复用场景。

首次最长主线程任务的中位数：Canvas2D 5.065→2.377 秒、WebGL2 4.829→2.276 秒、
WebGPU 4.976→2.475 秒。原生 ArcCollection/DisplayArcs 和注册索引仍含同步工作，
导入期间仍需等待这些同步阶段。真实交互仍有长任务；最终 WebGPU 三轮中的最坏值为 452 ms，
Canvas2D 约 1 秒，交互长任务仍是后续优化对象。

进程组峰值 RSS 中位数为 Canvas2D 3.858 GiB、WebGL2 3.783 GiB、WebGPU 4.092 GiB。
RSS 含共享页和浏览器子进程；GPU 独占显存需另行采集。本轮 RSS 与基线波动范围重叠。
16× WebGL2 稳定帧 CPU 提交约 5.40→7.65 ms，draw calls 527→1,118；复用更大覆盖的
代价必须保留在评估中。该视图 GPU pass 约 12.76→13.55 ms。所有稳定样本无新几何上传。

最终验收：全库 4,200 passed、56 skipped；相关三后端浏览器回归 70 passed，
GeoPackage 导入/主线程等价/取消浏览器回归另 3 passed。九次真实文件加载全部通过，
20 个表和 5,028,831 条源记录与只读 SQLite 核对一致；6,927,879 条弧、31,978,740 个
弧顶点保持一致。无页面/地图错误、控制台警告或失败请求，释放后 Worker 为零，
GPU 已跟踪资源归零；原文件哈希未变化，计时期间被测源码哈希未变化。

取每后端第一轮的全图、4×、16×、32×、回全图共 15 个固定画面，与基线同后端逐像素
比较均无差异，像素结论覆盖这 15 对同后端固定画面。
Windows、Firefox/WebKit 和这份文件的 DPR 2 需另行验证。各阶段可并行，分别报告阶段累计值与总墙钟，
CPU 提交、GPU pass、完整就绪和 FPS 使用各自的测量入口。
