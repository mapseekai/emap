# 正式 GPU：几何缓存、索引与稳定批次效率

本轮接续 `luma-binary-batch-optimization.md` 和 `remaining-performance-audit` 诊断。
现有 topology dataset、图层 API、半像素描边精度、Point LOD 和原始数据不变。
数值键缓存、紧凑索引、描边合批与跨 LOD 规划复用沿用现有运行时依赖和 Worker 并发配置。

## 已实施

### 数值键与常数成本 LRU

Worker 要素缓存按 source / namespace 分层，再按数值 feature ID 查询，不为每个要素创建 JSON 键。
显式双向链表维护 LRU，不通过不断删除/重插 Map 键更新顺序，也不重复从已删除槽位中寻找最旧项。
坐标和环偏移仍逐项验证；命名空间、几何编辑、跨 source 隔离不变。空结果仍不挤占复杂面缓存。
预算保持 64 MiB / 20,000 条，并对元数据保守计费。

### 稳定基数排序与紧凑索引

Morton 编码采用四次稳定字节基数排序，按原 triangle ID 保持相同编码的顺序。
顶点、三角形和绕向不变；复制索引及顶点时减少逐元素 subarray 临时对象。

分块填充最多有 65,535 个索引元素，局部最大顶点 ID 不超过 65,534，因此使用 uint16 索引。
超过条件的即时网格仍支持 uint32，索引宽度按每个网格的实际范围选择。
WebGL indexed offset 按索引字节宽度计算，WebGPU 使用元素下标；奇数个 uint16 索引上传时补齐
四字节写入边界，但不增加实际 draw count。GPU 预算和统计包含这部分对齐填充。

### 相邻描边块的有界合批

保留原细块的紧包围盒及逐弧过滤。对大弧集合先剔除不需要的细块，再按固定组拼接相邻块。
一组最多四个连续逻辑块、约一百万源顶点；单个超大块隔离，原二百万顶点绝对任务上限不变。
合并发生在一个请求/样式桶内，保留原成员和 signed arc 顺序，不跨父图层、样式或图标有序页。
GPU 仍按小缓冲上限拆分；保留路径邻居、端点标志和累计虚线距离。

稳定任务和绘制批次在既有缓冲预算内合并。
代价是边界块成员变化时，可能需要重建更大的合并批次；进出覆盖按实际成员变化创建新任务。

### 跨 LOD 的空间规划复用

保留已经完成的低/高细节空间计划，避免返回旧 LOD 时重复建立相同的分区。
保留精确 ArcCollection 身份，不错误共用不同 LOD 的包围盒；源移除、版本变化清理旧计划。
所有计划元数据一起统计，非活跃计划按 LRU 淘汰（128 MiB / 64 计划的保留目标）；当前引用的
计划在活跃使用期间保留。此目标管理计划缓存；原始 dataset 与浏览器其他资源分别计量。
GPU mesh 是否能够复用仍取决于驻留、成员和精度，复用计划不意味着所有几何永久驻留。

### 主线程坐标打包

保留精确计数/写入两次扫描，但是 arc/ring 内循环同步执行，仅在真实时间片边界 await。
不为每条短弧创建 Promise；长环仍分时，取消及原始自定义 iterator 的所有权约束不变。

## 测量方法

同一本地 Brandenburg GeoPackage，20 表、5,028,831 要素，原文件只读和 SHA-256 核验。
同机 Chrome、1280 × 852 CSS px、DPR=1、同样式和默认预算。
修改前后使用相同的一轮真实滚轮/拖动/退远和固定 4/16/32/1× 路线，各视图八次稳定重绘。
另外两后端各跑三轮导航，作为稳定性测试，不把不同轮数的累计工作量直接比较。
只运行一个压测浏览器，测量期间不并行构建或跑其他测试。文件系统缓存未清空，数字记录本次单轮样本。
暖帧表为八次 CPU 绘制/提交中位数，端到端帧率和 GPU 执行时间需独立采集。
冷更新的静默确认约 0.5 秒已包含在等待里。文件导入和读取时间不归到本轮渲染收益中。

可复测：

```sh
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgl2 --cycles 1 --warm-frames 8
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgpu --cycles 1 --warm-frames 8
```

原始对照、截图和备份在 `test-results/geometry-efficiency-round/`，未上传用户数据。

## 后续优化方向

GeoPackage 的巨型结果消息、属性恢复和首次业务索引仍有主线程成本；本轮不改导入协议。
尚未启用多 Worker、跨任务的通用 GPU 分页分配器或 RenderBundle，也没有增加显存上限。
这些范围分别优化和测量，本轮收益对应上述局部改造。

### 空间、工作量与正确性

- 全图填充三角形均为 3,788,004，原始要素和顶点未删减。
- 全图 Worker 任务 5,037 → 3,177；主线程打包累计约0.98–1.12秒 → 0.72–0.74秒。
- 返回全图后累计分区构建从36降为24，保留旧LOD规划，并按当前视图继续生成所需几何任务。
- 全图索引存储43.35 → 21.68 MiB；4×索引100.63 → 50.31 MiB，包括GPU四字节对齐。
- 几何缓存峰值：WebGL2 460.4 → 409.4 MiB；WebGPU 458.3 → 407.3 MiB。
- CPU 空间计划可以多保留一份LOD元数据（本路线约37→74 MiB）；原始数据和其他分配不在上述几何统计内。浏览器 RSS 变化需独立采样。
- 两后端×五个固定视图，避开UI覆盖的相同780×760区域（左上480,70）截图逐像素一致；UI计时文本不同，不声明全页哈希一致。
- 原文件逐表行数、总要素和SHA-256核验不变；GPU Buffer、几何缓存、计划及Worker在销毁后归零，末尾非计时GC存活JS约9MiB。
