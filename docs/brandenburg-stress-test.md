# Brandenburg GeoPackage：完整导入与浏览器压测

本报告记录本地真实 GeoPackage 的专项测试，不以较小夹具或关闭拓扑的预览代替全量导入。

> 本文保留原始稳定性压测记录。后续二进制批次优化及新的改前/改后实测见
> [二进制几何与批次效率](luma-binary-batch-optimization.md)，不要把下方历史耗时当作最新实现。

## 输入与复测方法

- 文件：`brandenburg.gpkg`，1,048,797,184 字节，20 个矢量表，5,028,831 个要素。
- SHA-256：`ad10a22c200a78278355c58cd927b2c5f667b6c406e5b05367ede1cd2b131f89`。
- 原生 SQLite 使用只读 immutable 连接逐表 `COUNT(*)`，与浏览器导入元数据逐表核对；开始和结束核对文件哈希。
- 实际 GeoPackage 查看器，默认 Worker 导入、共享拓扑、DisplayArcs、点 LOD、各图层样式和几何预算均保留。
- 独立 Chrome，每次只启动一个测试浏览器；只向 loopback 示例服务发请求，不上传或改写原始文件。

```sh
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgl2 --cycles 3
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgpu --cycles 3
```

脚本还支持 canvas2d。需要 Chrome、Python 3 的只读 SQLite 和 ps。默认输出到 git 忽略的
`test-results/geopackage-browser/`，包含 input.json、result.json、trace.jsonl 和截图。
每轮独立计时文件读取、source 导入、source 注册和 GPU 帧提交；完整帧需确认无 pending 几何、
无导航、无排队重绘且条目仍驻留，不能只看页面“导入完成”。连续手势与固定 4/16/32 倍视图分开。

## 实际发现并修复的问题

1. 帧开始后、后续图层尚未注册请求时，即时缓冲分配会把其上一帧已就绪几何当作可淘汰对象。
   请求仍保留 ready 状态，却已无 GPU mesh。增加帧收集保护、驻留性验证和重新入队回归测试。
2. 仅在绘制时裁剪三角形，不能减少先前上传的完整面存储。在部分近景中工作集触发 512 MiB
   保护。增加 Worker 侧保守上传覆盖和顶点压紧，完整源要素和拓扑保留，不提高预算。

初始旧测试虽能导入和显示全图，持续导航仍有失败，不能列为最终通过记录。512 MiB 报错
是明确的内存保护，与页面进程崩溃分别记录。

## 测量边界

RSS 为 ps 对本次浏览器及其子进程的采样合计，可能包含共享页，不等于 JS 堆、总系统内存或
GPU 独占显存。CDP 分别记录 usedSize/backingStorageSize。强制 GC 仅用于计时结束后的存活检查。
浏览器帧提交时间不等于屏幕呈现延迟。操作等待包含轮询确认，不换算成 FPS。
首次主线程恢复、LOD 和业务索引仍可能形成长任务；能稳定导入不代表所有交互已经低延迟。

## 最终验收记录

2026-09-24，本机 16 GiB Mac、Chrome，地图区域 1280 × 852 CSS px、DPR=1。
WebGL2/WebGPU 分别三轮真实滚轮放大、20 次鼠标移动、退远，Canvas2D 作为对照运行一轮。
三种后端都追加固定 4×、16×、32×、1× 视图；逐步等待导航结束、重绘队列清空、几何准备完成。

### 导入和首次完整就绪

| 后端 | source 导入阶段（秒） | 文件选择至确认完整就绪（秒） | 浏览器进程组峰值 RSS（GiB） | 最终结果 |
| --- | ---: | ---: | ---: | --- |
| canvas2d | 42.4 | 47.6 | 4.08 | passed |
| webgl2 | 44.6 | 76.7 | 3.67 | passed |
| webgpu | 43.0 | 61.7 | 4.40 | passed |

source 导入阶段包括 SQLite/几何解码、共享拓扑及主线程恢复，不只统计读取磁盘。
首次完整就绪包括文件读取、导入、source 注册和正式渲染；此处以脚本观察为准，会包含轮询延迟。
GPU 首个非空场景提交分别约为 WebGL2 47.1 秒、WebGPU 45.5 秒（从文件开始读取算起），
不是文件选择后 100 ms 即可看见 500 万要素。文件系统缓存未清空，以上不是冷磁盘 I/O 基准。
各后端记录为本轮独立浏览器实测，不是多次性能跑分中位数。

### 固定视图的完整更新等待

| 后端 | 4×（秒） | 16×（秒） | 32×（秒） | 回到 1×（秒） |
| --- | ---: | ---: | ---: | ---: |
| canvas2d | 1.9 | 1.6 | 1.4 | 1.4 |
| webgl2 | 30.9 | 7.9 | 7.3 | 29.8 |

固定视图通过诊断 AffineTransform 精确设定倍率，真实滚轮/拖动另行测试，不能把诊断相机
设置等同于所有 UI 控件均已验收。等待包含三次静默轮询确认约 0.5 秒；不是纯 GPU 时间或 FPS。

| 后端 | 真实导航循环数 | 单步骤完整更新等待范围（秒） | 页面/地图错误数 | 释放后 Worker 数 |
| --- | ---: | ---: | ---: | ---: |
| canvas2d | 1 | 1.2–1.4 | 0 | 0 |
| webgl2 | 3 | 11.5–21.9 | 0 | 0 |
| webgpu | 3 | 4.2–7.6 | 0 | 0 |

三个运行在导入后及最终均保留 5,028,831 条要素记录，20 个表的行数与原生 SQLite 一致。
共享 ArcCollection 为 6,927,879 条弧、31,978,740 个弧顶点（不含独立点表坐标）。
全部文件哈希未变化；没有用前 N 行、关闭拓扑、稀释输入数据或增大内存预算来通过测试。
点 LOD 和 DisplayArcs 仍按正式默认显示策略工作，全量导入不等于每帧绘制全部原始点/顶点。

### 工作集与释放

| 后端 | 跟踪几何缓存峰值（MiB） | dispose 后 GC 存活 JS（MiB） | dispose 后 backing storage（MiB） |
| --- | ---: | ---: | ---: |
| canvas2d | 0.0 | 7.17 | 4.79 |
| webgl2 | 458.1 | 8.94 | 4.79 |
| webgpu | 458.1 | 8.90 | 4.79 |

Canvas2D 的几何缓存列为 0 表示它不使用该 GPU 缓存，不表示零内存。两 GPU 后端最终
liveBufferBytes、geometryChunks.bytes、partitionBytes 及相关 Worker 均为零。GC 只在末尾
非计时检查点执行；RSS/JS/backing-storage 不能简单相加或互相等同。

4× 的当前跟踪几何约 457.8 MiB，仍明显高于软预算但低于 512 MiB 硬保护；其他机器、DPR、
视口、位置和不同样式仍须另外验证，不能用本路线承诺任何大数据都不触发保护。

## 仍然存在的性能成本

这份文件的 Canvas2D 完整就绪和冷视图更新快于 GPU，不能将“通过稳定性测试”表述为
“GPU 已全面快于 Canvas”。本轮每后端均观测到约 5.8–5.9 秒主线程长任务，因此仍会短时卡顿。
全图有约 6,695 个几何绘制块；频繁渐进重绘、块级 GPU 提交、缓存淘汰后的重建，以及近景
恢复完整面三角网都仍有开销。后续应分别测量批次合并、渐进重绘调度及导入后的主线程恢复，
不能把全部等待归因于显卡，也不能把原先历史崩溃直接断言为仅由本轮两个问题导致。

## 回归证据

- 最终全库：4,083 passed、56 skipped。
- 正式 GPU/渐进/分块浏览器回归：37 passed；其中新增两套后端的冷视图存储压紧像素等价检查。
- 工作集边界有失败复现：旧代码 3 个请求中一个条目被淘汰，仍错误宣告 ready；修复后请求和 GPU 驻留一致。
- 冷近景正确性用完整含孔洞 MultiPolygon，对比未裁剪上传的参考画面哈希相同；移动到另一覆盖区可恢复其几何。
- 原始压力日志、截图和 JSON 位于 `test-results/brandenburg-stress/final-webgl2`、`final-webgpu`、`final-canvas2d`。
- 中间失败运行保留，不计入最终通过次数。未测试 Firefox/WebKit；本轮大文件为 DPR=1。
