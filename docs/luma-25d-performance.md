# luma 2.5D 矢量性能回归修复

日期：2026-09-23。对照入口是用户指定的 `examples/luma-benchmark/`。

## 已确认的原因

第一版 2.5D 页面关闭了点聚合、描边屏幕过滤与快照导航，切回二维也没有恢复。
共享 renderer 还在检测到透视状态时主动绕过这三项优化。因此相同源数据会提交更多
几何，拖动时每次重绘原始图形；这不是把 GPU 换回 Canvas2D，也不是文件解码变慢。

修复保留 luma WebGL2/WebGPU 绘制。Worker 按透视后的屏幕坐标过滤描边，点网格
采用近侧采样尺度并保留原始代表点；完成帧的临时地面重投影避免手势内反复提交几何。
二维仍使用原来的 affine 快照路径。屏幕缓存键包含相机状态，最终停止后刷新真实视图。

2.5D 入口仅准备当前视口需要的显示缓存，benchmark 仍默认准备全量 A/B 缓冲。
该策略不减少 GeoJSON 的完整解析，也不降低面填充或原始拓扑精度。

## 同条件实测

设备为本地 Mac mini，Chrome headless / WebGL2；两个页面的地图区域均固定为
960 × 640 CSS px，DPR=1。数据是本地完整 `points.geojson` 和 `lucc.geojson`，
不是生成的压测替代数据。每次重新打开页面加载，执行相同 60 次鼠标移动并等待结束。
下列加载时间不是清空操作系统文件缓存后的磁盘冷读，单次墙钟波动不能当成稳定加速比。

| 指标 | 修复前 2.5D | 修复后 2.5D | benchmark 对照 |
| --- | ---: | ---: | ---: |
| 点文件：绘制点数 | 250,988 | 20,679 | 20,679 |
| LUCC：描边提交线段数 | 3,724,779 | 893,832 | 1,321,818 |
| 一段拖动的几何帧提交次数 | 61 | 1 | 1 |
| 点文件：页面加载墙钟 | 1,907 ms | 2,082 ms | 2,160 ms |
| LUCC：页面加载墙钟 | 15,403 ms | 15,049 ms | 15,659 ms |

2.5D 使用默认 pitch=50、bearing=-25；benchmark 为平面视图。倾斜及完整范围适配
会改变显示密度，因此 LUCC 的 893,832 与 1,321,818 不能解释为相同相机下的差异。
切回二维后，新页与 benchmark 都提交 **1,321,818** 条 LUCC 描边线段和 **20,679** 个点。
这里点聚合和描边过滤是显示策略，原始数据不改变；关闭控件可以查看原始显示。

两份数据本轮的帧间隔 p95 都约为 16.7–16.8 ms，设备多数时候已接近 60 Hz 上限。
因此结论是消除了多余提交与优化缺失，而不是证明 FPS 提高 61 倍或文件读取明显变快。
LUCC 的首次加载仍约 15 秒，复杂面准备不能被快照导航消除。

本机原始记录保存在 `test-results/luma-25d-perf/before-webgl.json` 和
`test-results/luma-25d-perf/after-webgl.json`。该目录被忽略，不作为包资源发布。

## 验证说明

整库单元/集成测试为 3,826 项通过、56 项跳过。
额外运行的旧 benchmark 浏览器回归中，导航与屏幕过滤的 8 项通过；
PointLod 有 2 项断言未通过：测试要求 16× 视图为 `full`，实际仍为 `point-lod`。
没有改写这两项断言或计为通过，也尚未独立确认该差异在本次修改前是否存在。
这限制了“全部浏览器回归均通过”的结论，不改变本记录中已测得的提交量与加载墙钟。
