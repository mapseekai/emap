# 正式 GPU：有效描边实例、仿射连接预计算与直接上传缓冲页

日期：2026-09-24。接续 `luma-render-next-audit.md` 的 CPU/GPU 分离诊断。
本轮只修改正式地图的渲染准备、GPU 数据布局和提交；GeoPackage 读取、解码、拓扑构建和结果恢复未改动。
保留原生 topology dataset、编辑/撤销、图层顺序、点 LOD、显示弧、4 倍 MSAA 和既有资源保护。

## 实现范围

### 有效线段和二维实线连接预计算

`compact-stroke.ts` 从已筛选的屏幕路径生成只含有效线段的紧凑布局：两个 high/low 端点，
以及两端的宽度无关连接系数。闭合环、反向线段、端帽和内侧连接限制仍保留。
每帧只计算当前线段的投影/方向及线宽限制，不重复计算全部邻接点的连接关系。
没有删除原始要素、非零线段或源坐标，也没有改变默认屏幕过滤精度档位。

适用条件为正式二维、不透明实线、MSAA 路径和正的等比屏幕变换。已准备屏幕网格在平移及等比缩放时
可重投影；不等比缩放、翻转、透视、虚线、箭头和半透明绘制不误用该布局。
原始共享邻接格式仍保留。紧凑布局的字节成本超过原布局的 1.125 倍时不转换，避免长线重复端点增大存储。
该路径减少冗余实例；保留原布局的长路径仍带有 padding。

GLSL/WGSL 均保留原有六顶点/十二索引包络、MSAA 采样、同色覆盖深度及 fragment discard 规则。
预计算改变了浮点计算顺序，边缘 MSAA 舍入可能有稀疏像素差异；下方像素对照记录这些差异。
`screenPathFiltering: false` 仍可使用原始路径。临时编辑几何和实验透视链路没有改成这个专用格式。

### 第一次上传即使用共享 GPU 缓冲页

`buffer-pages.ts` 对紧凑描边和可使用 uint16 的填充分块分配有界物理页，第一次创建就写入页内区间。
不把已经上传的完整场景再复制一份，不对源几何创建常驻 Arrow 副本，不进行无限扩容。
非紧凑长路径、点/图标及大 uint32 mesh 继续原资源路径。

页容量依据实际顶点/索引比例分配，通常以总 512 KiB 为目标；单个较大有界 mesh 可以独占一页。
填充页顶点数不超过 uint16 范围。绘制时根据索引字节宽度与页起点正确计算 WebGL offset / WebGPU firstIndex。
为同时保证四字节上传对齐和连续三角形批次，索引区间以完整零面积三角形补齐至 12 字节倍数；
它们不产生像素，`fillFramePaddingTriangles` 单独统计，不混入有效三角形计数。

逻辑块依旧独立，可见性/数据版本/过滤依旧由缓存条目管理。物理页只按 source/layer/格式区分，
允许已经释放的字节区间被新 LOD 使用；不把不同屏幕基准、绘制样式或父图层混画。
按原命令顺序仅合并同页连续区间。被释放、仍未就绪或者不在选择中的区间不会被跨越绘制。
存在细粒度三角形裁剪时继续逐范围提交，保持原有裁剪精度。

每个 slice 引用计数释放，空页立即销毁；失效旧条目不得覆盖新条目，上传失败不提交占用，
释放后的区间可安全复用。设备丢失/销毁时页分配器与其 Device 一起清理。

### 预算与诊断

256 MiB 软预算 / 512 MiB 总工作集保护没有提高。
共享页的未使用/已回收碎片空间通过 `geometryPages.slackBytes` 计入共同分配检查，
并在原预算内预留最多 16 MiB 的新页增长空间，计入同一显存额度。
已有 slice 释放后碎片可以暂超过 16 MiB，实际值仍参与保护；没有新额度时按精确需求分配。
保持多个活跃 slice 的页不会因为其中一个条目淘汰而被提前销毁。

`geometryChunks.bytes` 是条目数据和元数据，`geometryPages.allocatedBytes` 是共享页物理容量，
二者有重叠，按各自口径列出。工作集检查使用条目 + 小几何缓存 + 实际页 slack；
`liveBufferBytes` 统计几何 GPU Buffer 物理容量；slice 载荷另行统计。
原始 dataset、字体/图像、分区索引、Worker 临时数据和驱动内存仍需另外观察。

## 同数据前后测量

使用原 Brandenburg 20 表、5,028,831 条要素完整输入、同机 Chrome/Mac、DPR=1、
1280×852 CSS px 地图区域，原始文件 SHA-256 和各表记录数均核对。
修改前与最终版本均执行一轮真实滚轮/平移/退远及固定 4/16/32/1×。
各稳定视图先测八次 CPU 绘制提交（此时 GPU 计时关闭），随后测十二次硬件 timestamp 通道耗时；
通过异步 fence/queue completion 串行收集，没有使用 gl.finish 卡住交互。
时间为同机本轮样本中位数；跨机器和完整导入需另行重复采样；没有清空文件系统缓存。
CPU 与 GPU 有重叠/排队关系，不直接相加，不将任一列转换成帧率。

原始结果：`test-results/stroke-render-round/`。
`before-*` 是本轮基线，`compact-*` 隔离描边收益，`optimized-*` 是最终实现的同路线测量；
`pages-*`、`final-*` 是分配器调优阶段，不混入最终对照。不同导航轮数的累计指标不横向相加。

### CPU 提交 / GPU 渲染通道

| 视图 | WebGL2 CPU 前→后 ms | WebGL2 GPU 前→后 ms | WebGPU CPU 前→后 ms | WebGPU GPU 前→后 ms |
| --- | ---: | ---: | ---: | ---: |
| 全图 | 20.75 → 10.50 | 33.58 → 24.61 | 8.75 → 5.60 | 44.63 → 35.85 |
| 4× | 21.10 → 18.85 | 46.08 → 38.42 | 9.70 → 10.75 | 59.80 → 52.17 |
| 16× | 6.90 → 6.45 | 15.63 → 13.90 | 3.45 → 3.95 | 22.02 → 19.73 |
| 32× | 5.60 → 5.25 | 5.54 → 6.12 | 2.65 → 4.00 | 6.00 → 5.08 |
| 返回全图 | 20.80 → 15.30 | 33.58 → 24.69 | 9.00 → 8.10 | 44.70 → 36.18 |

全图两后端 draw call 从 3,151 次降至 1,367 次。返回全图受物理页碎片影响分别为 1,939/1,875 次，
合批率随视图和页分配历史变化。暖样本无新增几何上传。
4×/16×的 WebGPU CPU 提交时间增加；32× WebGL2 的 GPU 时间略增，说明短路径占比较低的近景收益不稳定。

描边专项：首次全图路径实例 4,554,616 → 2,324,584，原非零线段 2,009,974 保持；
长路径回退仍可能带 padding。完整场景的有效填充三角形仍为 3,788,004。

### 冷视图与资源交换

| 视图完整更新（秒） | WebGL2 前→后 | WebGPU 前→后 |
| --- | ---: | ---: |
| 4× | 5.848 → 6.346 | 6.065 → 6.444 |
| 16× | 1.448 → 2.527 | 1.700 → 1.700 |
| 32× | 1.142 → 1.153 | 1.143 → 1.398 |
| 返回全图 | 3.739 → 3.697 | 3.446 → 3.459 |

这轮主要改善已就绪场景反复绘制的成本；连接预计算增加一次性 Worker 工作，表中多数冷视图等待增加。
不将上一轮准备阶段的收益套用到本轮，不把文件导入等待归到渲染收益。

GPU 条目峰值约398 MiB，但共享页 slack 需额外计入同一预算，物理显存变化按实际 Buffer 容量评估。
本轮全图页 slack 约11.2 MiB，4×约17.1–18.3 MiB，退远约19.5–20.4 MiB；
实际物理 Buffer、页容量、片段和引用释放分别记录。

## 画面及回归验证

十组同后端固定地图区域比较（每组780×760像素，排除UI计时文本）：
共享页版本相对紧凑描边但独立缓冲的版本，全部零像素差异；
相对原描边 shader，每组0–4个边界像素不同，最大通道差38。该结果记录浮点预计算带来的实际差异，
验证范围为上述十组固定地图区域。

专项真实后端回归覆盖闭合/开口/折线、多种线宽、透明/虚线回退、旧画面导航、非等比回退、
共享slice合并/过滤/回收、uint16偏移、上传失败、源移除和编辑撤销。

## 最终验收与复测

续接检查保留以上生产实现与测量口径，补齐回收槽位索引上传失败、新页索引分配失败、
uint16 顶点上界，以及两后端连续过滤/恢复三次后的画面和页释放回归。

- 最终整库：4,126 项通过，56 项按既有条件跳过。没有删除或跳过原有 GPU 测试。
- Chrome 正式渲染/渐进/分块 45 项通过；2.5D、Icon、MSDF、Symbol 32 项通过；
  最终紧凑描边专项 6 项通过（其中 2 项为前述用例重跑），共 81 项不同的浏览器用例通过。
- 真实 points.geojson、building.geojson、lucc.geojson × 两种 GPU 后端，六组完整场景、
  近远景、实际导航及销毁检查通过，无地图/页面错误。
- Brandenburg 同路线前后比较及最终各三轮连续导航均完成；逐表计数、源哈希和释放检查通过。
- 构建、类型契约、文档、lint/格式、架构和发布资源检查通过；源码改动未进入导入链路。
- 压测为 Chrome / DPR=1；紧凑描边另有 DPR=2 专项，不声称此大文件在任意 DPR、
  浏览器和机器上都具有相同吞吐或内存需求。Firefox/WebKit 本轮未重新完整验收。

使用正式发布示例复测，不需要私有原型或修改默认参数：

```sh
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgl2 --cycles 1 --warm-frames 8 --gpu-frames 12
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgpu --cycles 1 --warm-frames 8 --gpu-frames 12
```

`--gpu-frames` 仅在硬件 timestamp 可用时记录样本；不可用时不填零冒充 GPU 耗时。
