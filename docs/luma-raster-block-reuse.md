# 原始源块 / GPU halo 复用与 UInt8 文件夹支持

## 源块复用与输入配置

本地 `luma集成` 工作区，HEAD `8384334e`。本轮及前几轮动态栅格工作仍未提交、未推送。
测试只读取完整授权文件：FUS TIFF、GJ_COG_zip.tif 和 cdf20250916042716 内五份 TIFF。
没有重写、转换、生成金字塔或上传原数据；性能由下述实测结果评估。

新目录含四份 UInt8 RGB 未压缩逐行 TIFF 和同名 `.tif.ovr`；外部 OVR 为 128×128、
平面分离、未压缩、8 层。`J50D002005_cog.tif` 为 UInt8 RGB、512×512 DEFLATE，含
7 个内部 IFD（包括原图）。五份均有 EPSG:4326 坐标键。TFW/XML 不作为本轮地理定位来源。

## 新的数据路径

保留原始 RasterSource.readWindow 合约，增加可选 readTexture：原始数值一次组织为
interleaved RGBA8/16 存储布局，未使用通道为0，原始数值、透明度语义与 UInt16 位深保持不变。
压缩块解码后直接填充该输出，不先建立三份完整波段平面再交给主线程重新打包。
Worker 将唯一输出 ArrayBuffer 转移给主线程，luma 按行跨度、字节偏移直接上传子矩形。
纹理采用 rgba8uint / rgba16uint；RGB、alpha、NoData 和拉伸仍在 shader 解释。

合适的二维分块 TIFF 只读取不重叠 core。当前采样需要的1像素 halo 从已驻留邻块核心
GPU-to-GPU 复制，包含四角；不做插值、回读或 CPU 着色。不递归扩展邻块的 halo。
邻块依赖按实际视口的源像素足迹选择，补齐所需邻块纹理。
数据版本由源实例生命周期管理；缓存键含 level/位置，不因样式变化失效。

一个目标块需要的边缘准备完整后才发布对应区域。旧影像只覆盖尚未完成区域，NoData
和透明区域同样拥有独占覆盖；不会用不完整的 halo 冒充已完成细节。复制过的边缘可以
在邻块被淘汰后继续使用；重新创建目标纹理时才清空它的边缘状态。

## 内存和兼容性

上传输出每批最多8 MiB，packed path 每 Worker 最多两个物理解码同时执行，保留两个
源 Worker；传统 readWindow 默认四块解码并发不变。新输出字节额外计入源的64 MiB
并发解码预留；主线程完成队列有背压。普通 ArrayBuffer 压缩输入不再额外复制一次，
SharedArrayBuffer 仍转为普通内存后供原生解压流使用。

源解码缓存和显示纹理软预算仍各32 MiB，当前可见/过渡预算保持原设定；未增大缓存、
降低DPR、降低overview目标分辨率或量化原始数值。条带继续使用既有精确列窗口路径。
不适合core对齐或超过专用packed输出能力的窗口回退有界传统读取，不让待加载队列永久挂起。

默认 GPU 路径没有主线程打包数组，但 Worker 输出和浏览器上传仍有复制与分配。
输出组织与浏览器上传仍有复制成本。各内存统计存在包含/共享关系，峰值可能不同时发生，不直接相加。

## 文件夹使用

启动本地 examples 服务后打开 `/mapseekai/emap/examples/luma-raster/?gpu=webgl`
或 `?gpu=webgpu`。点击“选择文件夹”，选择 cdf20250916042716，使用文件下拉框逐个加载。
四个原图自动配对同目录同名 .tif.ovr，COG 直接使用内部层级；也可多选文件与 OVR。
相对路径匹配避免子目录同名文件串配。通过下拉框选择当前显示的影像，一次显示一份。

本独立示例提供 UInt8/UInt16 原生纹理路径；其他数值类型、调色板及跨 CRS 场景继续使用正式 Canvas。

## 最终实测与兼容修正（2026-09-22）

新目录中的 J50D001006.tif 原图为27119×18617，OVR的3390×2328层恰好是
两维各自除以8后向上取整。原有按较小缩减比例反推宽高的1像素误差规则误排除了它。
现在识别同一个整数缩减倍数的精确ceil尺寸，同时保留页、mask、波段、类型及已有
一般宽高比检查，并拒绝NaN/非整数尺寸。四个外部OVR原图均获得9层（含原图）。
该修正用于识别有效层；FUS/GJ前后使用相同层级。

### GJ 端到端与读取

每侧两轮，1280×678 CSS、DPR1。操作稳定时间含8帧确认；纹理准备时间不含该
确认窗口；GPU硬件执行时间需另行采集。读取量是单个动作的逻辑增量，物理磁盘流量需另行采集。

| 动作 | 后端 | 稳定 ms 前→后 | 纹理准备 ms 前→后 | 逻辑MiB 前→后 | 解码块 前→后 |
|---|---|---:|---:|---:|---:|
| zoom-4x | webgl | 233–249 → 183–200 | 87.1–106.5 → 42–51.8 | 19.95 → 5.25 | 32 → 8 |
| zoom-16x | webgl | 250 → 182–184 | 103.6–104.4 → 38.4–39.6 | 18.16 → 4.43 | 32 → 8 |
| zoom-4x | webgpu | 250 → 198–200 | 106.9–107.2 → 56.5–59.4 | 19.95 → 5.25 | 32 → 8 |
| zoom-16x | webgpu | 250 → 200 | 105.1–106.4 → 55.2–55.8 | 18.16 → 4.43 | 32 → 8 |

上述两个视图均保留8张原始数值纹理。CPU上传核心16 MiB，GPU另外复制约80 KiB
边缘/四角；原始核心像素保持完整。主线程packMs=0，但Worker仍有数据组织与复制。
样式变化不重读源块或重新上传纹理；缓存淘汰后重访旧视图仍可能发生读取。
其他视图的收益不一，FUS条带仍使用原有精确列窗口路径，不把GJ结果外推到所有文件。

### GJ 临时缓冲

1920×858 CSS、DPR2，每次只打开GJ，3轮缩放/平移、真实滚轮/拖动、重新加载、卸载。
优化后三次运行均列入峰值范围，避免只挑最低一轮。约250ms采样可能漏过瞬时峰值；
Worker按isolateId去重。backing storage包含数组缓冲和其他外部存储，不等于纯解码数组。

| 后端 | Worker峰值前 MiB | Worker峰值后范围 MiB | 主页面峰值前 MiB | 主页面峰值后范围 MiB |
|---|---:|---:|---:|---:|
| webgl | 181.6 | 91.5–121.2 | 28.0 | 32.6–57 |
| webgpu | 189.0 | 92.7–114.6 | 29.4 | 26.7–36.7 |

GC检查点的Worker缓冲前后均约31 MiB，本轮主要减少临时工作集，常驻缓存规模保持相同。
GPU数值纹理采样峰值约30.6–36.3 MiB；可见/过渡资源可能超过32 MiB软预算。
WebGL主页面缓冲峰值上升，WebGPU也有波动：传输的RGBA布局需要4通道，队列中仍可能
保留多批8 MiB输出。各层内存按本轮实测变化分别报告；各列峰值发生时间不同，
与进程footprint也存在重叠，分别列出。浏览器上传包含数据复制，驱动与交换缓冲仍有另外的占用。

最终内存运行各GPU后端导航中都出现过一帧约33.3ms，无50ms以上主线程长任务。
Headless rAF记录回调间隔；前台呈现与长时间掉帧需专项采样。生产不强制GC。
