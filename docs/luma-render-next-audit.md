# 渲染后续优化：GPU 描边与命令提交隔离诊断

日期：2026-09-24。范围仅为已加载矢量的渲染；未修改导入协议、生产源码、依赖、默认画质和预算。
本轮是诊断原型，不是新一轮已经接入正式 Painter 的优化。

## 证据和方法

完整 Brandenburg 原文件，20 表、5,028,831 要素。Chrome、Apple M4，1280×852 CSS px、DPR=1，MSAA=4。
两后端各在原文件完整导入后测试全图、4倍视图，以及同一驻留集合下平移31/-17 CSS px。
CPU记录绘制/提交时长；GPU使用现有luma timestamp-query的render-pass起止时间。
暖帧按正序和逆序测试，每个策略20个计时样本，丢弃预热；组件诊断每项6个样本。
帧间等待设备完成，避免积累队列；这不是连续手势FPS。GPU时间含pass执行边界开销，不能当作
单独顶点/片元着色器耗时，CPU/GPU也不能简单相加换算交互帧率。
原始代码和资源只读，源SHA-256、逐表计数、销毁后Buffer/Worker数核验。

原始输出：`test-results/render-next-audit/{webgl2,webgl2-cull,webgpu}/`。
`summary.json`为样本中位数，`pixel-diffs.json`为逐RGBA像素对照。
最后WebGL2结果取webgl2-cull，与WebGPU包含同样策略；第一次WebGL2用于原型验证。
外部API核验：[luma RenderBundleEncoder](https://luma.gl/docs/api-reference/generated/core/classes/RenderBundleEncoder)、
[luma多采样限制](https://luma.gl/docs/api-reference/generated/core/type-aliases/RenderBundleEncoderProps)、
[WebGL multi-draw规范](https://registry.khronos.org/webgl/extensions/WEBGL_multi_draw/)。

## 最大的新发现：GPU耗时主要在描边

| 视图/后端 | 完整场景 GPU ms | 仅面填充 GPU ms | 仅描边 GPU ms | 仅圆点 GPU ms |
| --- | ---: | ---: | ---: | ---: |
| 全图 WebGL2 | 33.52 | 3.35 | 29.60 | 0.79 |
| 全图 WebGPU | 44.63 | 2.88 | 38.86 | 0.85 |
| 4倍 WebGL2 | 46.15 | 5.84 | 38.55 | 1.16 |
| 4倍 WebGPU | 59.70 | 5.28 | 48.96 | 1.41 |

组件是排除其他图层后的诊断，不能相加、不能把隐藏内容列为优化。
将描边片元范围缩到1×1像素后，GPU仍约19–25ms，说明不能仅归因为片元混合；
剩余包括顶点、图元及驱动工作，不把差值称作某一GPU阶段的准确百分比。
同MSAA几何的reference控制路径明显更慢（全图约67ms、4倍约83–85ms），
不应丢掉当前不透明描边的覆盖优化，也没有通过关闭MSAA报告提速。

## 跨小mesh批量组织原型

固定已就绪命令集，只合并连续兼容绘制，保留高低位坐标、完整三角形、邻居与端点。
这不同于正式实现中每组最多4个逻辑块的准备批次。

| 全图 | 正式CPU ms | 合批CPU ms | 正式GPU ms | 合批GPU ms |
| --- | ---: | ---: | ---: | ---: |
| WebGL2 | 26.05 | 4.65 | 33.52 | 32.00 |
| WebGPU | 12.50 | 1.70 | 44.63 | 43.45 |

逻辑draw call为3151→210。减少命令提交有效，但GPU时间并未同比降低；不能说FPS提高5倍。
原型为了同页A/B另外保留CPU几何和生成合并GPU缓冲，额外GPU约220.63MiB，全图总约441.85MiB。
合并准备约0.16–0.21秒，不计入暖帧。不是低内存或冷加载提速的验收。
4倍时额外副本触及诊断500MiB分配界限，181组合并被跳过，故该视图合批仅降至2039次draw。
生产版本不能复制整个场景后再合并：应在初次上传时直接写有界页，追踪区间所有权和增量失效。
必须保留源、父图层、样式顺序、编辑/过滤/撤销、过期任务、页回收与原GPU保护。

## WebGPU RenderBundle原型

重放固定几何命令集，只更新5组已经绑定的样式/相机uniform；没有复制屏幕位图。
全图CPU约12.50→0.60ms、4倍约13.15→0.60ms，GPU仍约44.63/59.38ms。
日志中bundle的JS draw计数0仅表示这一帧调用executeBundles，实际仍重放3151/2498个draw。
不能把0次JS draw理解成没有GPU绘制或0.6ms整体帧时间。
当前安装的luma 10.0.0-alpha.1构造器明确拒绝sampleCount=4；本诊断使用原生WebGPU bundle，
复用现有管线、资源和4倍MSAA，未更换或修改依赖。原生结果不能当作当前luma公开接口已支持。
正式接入应先解决多采样兼容，并按资源世代/绘制集合/附件格式失效；不缓存整张可变地图一个永久bundle。
WebGL2没有等价原生RenderBundle，可先共用物理批次和预解析绘制状态；multi-draw只作能力检测后的增强。

## 下一轮 GPU 描边方向

当前path每记录7个Float32、每mesh末尾保留3个邻居记录。最新正式全图统计：
127,672,216路径字节、1702个path mesh，对应4,554,616个提交实例；实际非零线段为2,009,974。
约55.9%为邻居/分隔/无效实例；代码通过pathFlags>=4在顶点shader提前退出。
这是GPU提交的冗余实例比例，不是可以直接省下55.9%的GPU耗时。
候选改造：只对有效段生成绘制实例/索引，仍保留原邻居关系；以及2D实线专用管线，将方向、
连接角与端帽的可复用计算前移，避免每帧对相同邻接几何重复计算。
这些尚未实现。必须比较额外属性/带宽、显存、GPU实际时间和像素；不能直接删除padding破坏闭合线。
特殊投影、虚线、半透明、箭头保留已有路径或单独验收，保留MSAA与CSS宽度，不减少源要素。

简单将现有PathRangeIndex接到源锚定screen几何的原型没有减少两组视图的draw/GPU时间。
当前分组和范围粒度下，不能把它当作下一轮主要提速措施；可能需要更细空间组织，而非只打开开关。

## 验证和边界

正式绘制、冻结命令重放、合批、screen-range候选、WebGPU原生bundle在全图/4倍视图和驻留集合
平移后，对相同780×760地图区域做24组逐像素比较，所有RGBA差异为0。不是全页/任意视图的等价证明。
新区域流入、冷构建、动态过滤、资源失效和编辑没有用原型覆盖；生产集成仍需完整回归。
三个诊断运行全部完成，无地图/页面错误；用户数据文件未修改，末尾GPU Buffer/Worker均为0。
未重新跑生产整库测试：生产文件哈希与开始时一致。本轮没有提交、推送、部署或创建外部任务。

优先级：GPU描边有效实例与专用计算路径；共享物理批次；WebGPU命令复用；冷几何复用作为后续。
导入留待用户指定的最后阶段，本报告不将任何导入工作纳入下一轮渲染提速目标。
