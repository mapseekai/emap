# 正式 GPU：有界几何微批次与原生弧段打包

日期：2026-09-24。接续 `luma-stroke-residency.md`，本轮处理渲染准备吞吐，
不改变文件导入、源拓扑、属性恢复、着色器、MSAA、显示 LOD 或用户样式。

## 实现

### 合并消息，不合并源要素或逻辑块

之前每个块都独立打包、发往几何 Worker，并等待它返回后才处理下一个块。
现在每个父图层/绘制请求的首个任务仍立即执行；随后将同一请求的小任务合为最多 8 个、总 transferable backing buffer
不超过 2 MiB 的微批次，同一时间仍只有一个批次、一个几何 Worker 在计算。
较大任务继续单独执行，原有单任务几何上限和 GPU 256/512 MiB 预算不变。

每个任务保留独立输入、源版本、要素 ID、三角化缓存键和 GPU 资源身份；
不同父图层/绘制请求不混在一个批次，避免上层慢任务阻挡下层的首批结果；
批次不是把坐标连接成一个新大 mesh。返回结果按各自归属登记，仍按图层顺序渐进绘制。
批次中的一个无效几何单独报错，不把其他成功结果判为失败；通信错误则终止该次 Worker。

打包前使用原生弧长和路径数作保守准入，不能为了凑批次先分配多个大包。
自定义迭代器无法安全估算时不追加到已有批次。打包和批量上传均保留分时让出，
首批反馈不等待凑满，完整几何就绪后立即通知，不改变取消/失败后的资源清理约束。

### 批量取消与驻留

整个批次的任务都登记为活跃，不能被软预算淘汰。普通相机变更允许仍有用的有界批次完成，
完全过期时取消；显式移除源或销毁地图会终止相关批次。迟到结果不能恢复已删除内容。
预留任务时游标会前移；取消后重新选中时会回退游标，避免出现一直 queued 却再也不调度的块。
已完成任务不会因同批其他任务取消而重复上传。

### 原生坐标打包少读一遍

未额外设置保留间隔的原生弧集合已经有每条弧的顶点数。符合条件时先按弧 ID/长度估计容量，
只读取一次坐标并去重共享端点；返回前压紧成拥有独立 backing buffer 的精确数组。
坐标、环次序、弧方向、孔洞和属性都不改变。

预测坐标容量最多 2 MiB，防止含大量重复点的巨型弧先分配巨大数组再裁短。
超过该容量、需应用保留间隔或自定义迭代器时，仍使用原来的精确计数/写入两遍流程；
这是快速路径的准入条件，不是新的源要素限制。长环时间片、取消及版本检查继续保留。
该路径可能暂时同时持有容量数组与压紧副本，额外瞬时容量受上述 2 MiB 限制，不能称为全程零复制。

## 计量与边界

`geometryChunks.messages` 是几何计算请求消息数，不含少量源保留控制消息；`jobs` 仍计成功逻辑任务。
`batchedJobs`、`maxBatchJobs` 表示参与微批次的任务总数和最大任务数；`peakInputBytes` 统计
当前已发批次的 transferable backing allocations。它不是浏览器总内存或 Worker 全部工作集。
`batchAdmissionMs` 单独记录新增准入成本，不能只看 `packMs` 就认为主线程准备已全部省掉。

传输仍只转移新打包且由渲染器拥有的缓冲，不分离用户 source 的坐标数组。
参考：[Worker postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Worker/postMessage)、
[Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)。
批次保存多个结果直到传回，短时输出驻留可能高于逐任务版本；GPU 预算和 Worker 64 MiB 要素缓存未提高。

本轮不声称降低了 GPU 着色器或片元覆盖成本。原生路径、逻辑块、页布局和绘制策略保持，
但调度顺序会影响物理页分配/缓存组成，因此暖帧合批率和内存不是每个视图固定相同。

原始记录：`test-results/render-throughput-round/`。`before-*` 是本轮基线，`batched-*` 为仅微批次阶段，
`final-*` 为未加入预测容量保护的打包试验；`verified-*` 为逐要素时间检查阶段；最终比较使用 `accepted-*`，不混用阶段或导航轮数。

## 最终同路线前后对照

完整 Brandenburg 原文件，20 表、5,028,831 要素。同机 Chrome/Apple M4，1280×852 CSS px 地图区域，
DPR=1、原 4×MSAA、原始样式/拓扑/LOD。每个后端独立执行同一轮滚轮、拖动、退远，
再执行固定全图→4×→16×→32×→全图；不并行跑其他压测，不清空文件系统缓存。
暖 CPU 12 次样本与 GPU timestamp 12 次样本分别测量，以下为同机本轮样本，不是多轮导入中位数。

### 准备与提交等待

| 项目 | WebGL2 前→后 | WebGPU 前→后 |
| --- | ---: | ---: |
| 首批非空场景至完整几何提交 | 3.779 → 3.327 秒 | 3.722 → 3.169 秒 |
| 首次全图 Worker 请求消息 | 3,177 → 470 次 | 3,177 → 463 次 |
| 首次全图逻辑任务 | 3,177 → 3,177 个 | 3,177 → 3,177 个 |
| 首次全图累计渲染帧 | 94 → 72 帧 | 93 → 71 帧 |
| 首次全图累计 draw | 36,350 → 28,696 次 | 35,867 → 27,102 次 |

首批至完整只统计已导入数据的几何提交跨度，不包含此前约40多秒导入。消息数统计几何请求，
修改前一任务一请求，因此直接等于成功任务数；微批次后逻辑任务和输出几何仍独立。
累计帧/draw 含少量示例启动内容，不是单帧绘制量。

| 固定视图完整更新 | WebGL2 前→后 秒 | WebGPU 前→后 秒 |
| --- | ---: | ---: |
| 4× | 6.939 → 5.623 | 6.571 → 5.819 |
| 16× | 1.701 → 2.017 | 2.012 → 2.061 |
| 32× | 1.146 → 1.471 | 1.433 → 1.186 |
| 返回全图 | 3.726 → 3.810 | 4.330 → 3.786 |

等待值含约0.5秒静默确认，不能当作纯三角化/GPU时间。4×的冷更新改善较明显，
16×/32×与退远不是每组都变快，不用首批改善代替全阶段提速。

### 坐标打包与新增准入成本

- webgl2：首次全图打包 687.8 → 551.2 ms；新增准入 100.9 ms。两项相加为 652.1 ms。Worker累计 1457.0 → 1544.6 ms。
- webgpu：首次全图打包 692.7 → 488.3 ms；新增准入 94.1 ms。两项相加为 582.4 ms。Worker累计 1479.2 → 1498.3 ms。

微批次减少等待和消息管理，不减少三角化本身，也不保证 Worker 算术时间变短。

### 暖帧渲染（CPU/GPU 单独计时，ms）

| 视图 | WebGL2 CPU 前→后 | WebGPU CPU 前→后 | WebGL2 GPU 前→后 | WebGPU GPU 前→后 |
| --- | ---: | ---: | ---: | ---: |
| 全图 | 7.60 → 7.40 | 3.60 → 3.90 | 23.57 → 24.20 | 35.62 → 35.23 |
| 4× | 15.55 → 16.95 | 8.15 → 10.95 | 35.17 → 35.45 | 48.73 → 49.09 |
| 16× | 5.90 → 5.80 | 2.80 → 3.20 | 14.41 → 13.75 | 18.12 → 18.15 |
| 32× | 4.35 → 4.45 | 2.55 → 2.75 | 5.34 → 5.44 | 5.96 → 5.96 |
| 返回全图 | 9.10 → 9.40 | 4.30 → 2.80 | 23.23 → 23.78 | 35.52 → 35.39 |

暖帧无新增几何上传。GPU时间没有一致改善，本轮没有修改shader。4×的CPU有所回退，
任务调度影响页分配和缓存组成，当前4×逻辑draw由WebGL2 1,865→2,092、WebGPU 1,874→2,099；
不能只报告消息下降而隐藏这项交换。相同源、相同视图并不保证不同加载历史下的物理页完全一致。
这轮保留有界微批次的冷准备收益，进一步的GPU着色、页碎片与物理合批仍须单独优化。
