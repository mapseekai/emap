# GeoPackage 4× 与回全图：几何准备优化

## 几何准备与取消保护

基线为 `8141f5d1`。本轮只优化显示几何的准备和重建，不改 GeoPackage 导入语义，
不关闭共享拓扑、不裁减源记录、不改变样式、默认 LOD、坐标精度或 MSAA 设置。
最终仍为每图一个懒启动几何 Worker；输入、GPU 和三角化缓存预算不变。
全图与近景的合计工作集超过软预算时，按既有淘汰策略重建所需尺度。

## 最终保留的改动

`geometryYield()` 保留原有异步定时器让步，仍在让步前后检查取消。
没有将原生 scheduler 或连续 microtask 作为新的默认调度策略。

分区过程中只取得一次 native vertex-data 视图，避免每条弧、每轮遍历都创建包装对象。
显示面少于三个 native 顶点时不排入三角化任务；不删除源要素，仍保留非闭合三角形。

仅严格凸的三角形和四边形走直接索引路径，保留 Earcut 的绕序、起始节点和耳切顺序。
凹面、退化面、更多顶点和不确定数值仍使用原 Earcut，没有近似三角化或改写坐标。
4,000 组随机回归覆盖闭合/非闭合、正反绕序、凹面、重复点和不同数值尺度。

补充 Worker 的交付时取消检查：成功消息已到达但 Promise continuation 尚未执行时，
abort/dispose 仍然拒绝失效结果；覆盖单任务与批任务四种取消/销毁组合。
原有传输所有权、单批在途、超时、错误上报和资源释放机制均保留。

## 实验结果与取舍

双 Worker 批内并行在早先记录中较快，但本轮交错 A/B 下 WebGL2 未稳定获益。
候选版 4× 中位数 6.428 秒，对照 6.247 秒；回全图 3.461 秒，对照 3.353 秒。
因此撤掉双路调度、缓存分割和新增协议字段，不用更多 Worker 换取未证实的收益。

GPU 完成反馈实验显著减少了渐进帧次数，但回访缓存使首个 4× 构建 1,531 个条目、
后续仅约 1,100 个；收益比较需对齐构建量。对照相近构建量后，
完整更新等待没有稳定下降，该实验同样未合入。实验日志与最终实测分开保存。
系统后台负载明显波动，测试没有关闭用户的其他程序或把较快样本单独挑作结论。

原生 `scheduler.yield()` 候选虽然通过正确性测试，但交互 RAF 间隔分布未显示稳定改善，
因此恢复原定时器让步，再对实际交付代码重新测量。候选样本单独保留，最终实现收益
以交付版数据为准；调度 API 对卡顿的影响仍需更充分的配对测量。

## 复测方式

```sh
pnpm build
pnpm examples:dev
```

从示例的 GeoPackage Viewer 选择完整文件，分别使用 WebGL2、WebGPU、Canvas2D。
要验证快路径，主库与 `emap-geometry-worker.js` 应同时来自本次构建；最终没有新增
Worker 协议字段或公共 API，宿主的 `geometryWorkerUrl` 用法不变。

自动化可使用 `pnpm examples:luma` 的生产预览，再执行：

```sh
pnpm benchmark:geopackage:browser --file '/本地数据/brandenburg.gpkg' --renderer webgl2 --cycles 1 --warm-frames 12 --gpu-frames 8
```

计时保留默认源精度、共享拓扑、样式和 LOD。新视图与缓存命中后的稳定重绘分开测量，
等待确认、CPU 提交、GPU pass 和 FPS 分别使用对应计时入口。

## 实测结果与结论边界（2026-09-25）

完整 `brandenburg.gpkg`：1,048,797,184 字节、20 个表、5,028,831 条记录。
M4 / 16 GiB / Chrome 153.0.8010.53；1280×852 CSS、DPR 1。独立生产构建，
同一文件与样式，不清空 OS 文件缓存。基线为本会话中独立运行的每后端三次记录；
撤销调度/并行实验后，交付版本另运行每后端三次，最终六次在基线之后执行。
后台系统负载变化明显，以下保留全部三次样本；严格隔离的提速结论需要空闲环境下的交错对照。

这组最终墙钟结果中，4× 和回全图的中位数变慢，性能目标仍待验证。
未修改的导入链路也出现较大波动；运行负载需要单独控制。
本轮确认了准备阶段重复工作减少和取消正确性。

确定性结果：首次全图与回全图需要构建的条目均由 3,177 降到 2,970（减少 207 个、约 6.5%）。
4× 仍需构建 1,531 个条目；回全图仍没有实现整幅几何常驻复用。分区元数据取得次数
通过方法级回归固定为一次，简单凸面索引与 Earcut 精确一致；这些不等同于整图提速比例。

4× 跟踪几何约 373.94 MiB，默认 256 MiB 软预算与 512 MiB 工作集保护没有提高。
要继续缩短界面等待，仍须在既有预算内减少跨 LOD 的表示/重建成本。
主线程耗时、GPU pass、轮询就绪与 RSS 分项报告。

## 正确性与发布边界

最终版本的六次大文件运行均成功，对照中的六次基线记录同样成功。每次表行数均与
原生只读 SQLite 核对：20 个表、5,028,831 记录、6,927,879 弧、31,978,740 弧顶点。
原文件哈希未变化，最终代码在性能采样期间没有变化。

两个 GPU 后端各五个固定视图共 10 对改前/改后画面，RGBA 逐像素差异均为零。
没有页面/地图错误、警告或失败请求；销毁后相关 Worker 和已跟踪 GPU 资源均为零。
像素结论覆盖上述 10 对同后端固定视图。

最终全库测试：4,207 passed、56 skipped；相关浏览器测试：74 passed、10 skipped。
未运行需要另外数据环境的跳过项，未验证 Windows 或本文件的大视口 DPR 2。

额外在稍后较低负载下重跑旧基线（各一次，仅作诊断）：WebGL2 4×/回全图为
6.155/3.600 秒，WebGPU 为 5.711/3.448 秒。这两个独立基线复核作为诊断样本保存，
三次中位数仍使用原样本。代码影响待空闲环境配对测试后判定。

本轮未提高缓存预算、未改变默认渲染后端或导入方式。实现与正确性验证已收尾，
“4× 和回全图明显更快”的性能目标尚未证明；提速发布需补充该目标的配对证据。
